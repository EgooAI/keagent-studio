# 本机压测基线

2026-11-03，Asia/Shanghai。优化前业务代码为 `ba4862686c499801a6a993f41eb45c03eddbed07`。后续正式版本基于 `f90eda6` 增加两行连接池配置，复测结果见下文。GitHub 默认分支为 `main`。

优化前功能在短时压测中没有意外错误，但并发增加后吞吐明显下降。诊断与临时对照确认 Go 默认连接池反复建连是本机的主要瓶颈。现已将最大打开连接数和最大空闲连接数均设为 20，并使用正式源码构建的二进制完成完整复测。

## 环境与方法

- Windows 11 / 10.0.26200，AMD Ryzen 7 6800H，16 逻辑处理器，15.2 GiB 内存；Node 24.20.0、PostgreSQL 18.3、Next.js 16.3.4 生产构建及编译后的 Go 二进制。
- 认证服务 18080、Go 18081、PostgreSQL 55432；全部在同一台机器，Node 原生 fetch 作为闭环驱动器。不是分布式压测，不含真实互联网延迟、TLS、浏览器渲染及桌面帧率。
- 每轮独立建立并迁移 `keagent_load_<随机ID>` 数据库，结束后关闭测试服务并删除该临时库。原 `keagent` 数据库的用户、房源、资源未参与测试。
- 20 个测试用户，每人 100 套房源、10 个待审核任务，共 40 个公共资源。初始工作区 JSON 约 29.6 KB，PostgreSQL 压缩存储约 2.3 KB。
- 混合负载：60% 工作区读取、20% 身份复核、10% 草稿保存、10% 用户资料更新。请求按固定序列分配到 20 个账号，其中写请求落到 4 个账号；另测单账号热点写入。
- 预热 3 秒，常规阶段各持续约 8 秒，统计包含阶段结束时的在途请求；并发表示同时在途请求数，不代表在线人数。无思考时间，不使用自动重试。
- JWT 在准备阶段由 SDK 正常签发，不将频繁登录混入业务吞吐。保留生产认证限流；单独以有界突发验证。真实 AI 密钥强制置空，不请求付费服务。

## 瓶颈诊断与临时对照

未改业务实现的诊断复测再现了吞吐下降。每阶段通过 PostgreSQL `pg_stat_database.sessions` 记录新增连接：10 并发约 502 个、30 并发 660 个、100 并发 703 个。该统计异步刷新，因此按约数解读。Go 的初始化未设置 `SetMaxIdleConns` / `SetMaxOpenConns`；默认仅保留少量空闲连接，高并发结束的连接频繁被关闭。

在 `output/load-test/pool-experiment` 临时复制源码，仅增加：

```go
db.SetMaxOpenConns(20)
db.SetMaxIdleConns(20)
```

用临时二进制、相同种子数据和负载进行对照，结果如下，均无意外错误：

| 并发 | 优化前吞吐 | 优化前 P95 | 优化前新增连接 | 临时池20吞吐 | 临时池20 P95 | 临时池20新增连接 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 10 | 239.0 | 156.58 | 502 | 1344.0 | 12.14 | 5 |
| 30 | 145.0 | 613.65 | 660 | 1693.2 | 26.09 | 10 |
| 100 | 152.5 | 2331.75 | 703 | 1889.1 | 73.21 | 0 |

30 并发下吞吐约提升 11.7 倍，P95 下降约 96%。高并发连接复用改善显著，支持优先调整 Go 连接池的结论；20 只是本机实验参数，正式设置需要结合实例数和 PostgreSQL 连接预算。

身份状态查询抽样 `EXPLAIN ANALYZE` 使用 Session 与 user 主键索引，执行耗时 0.051ms；采样也出现少量行锁/事务锁等待。当前证据不足以认定签名验证或身份 SQL 本身是主要瓶颈。仍需在复用连接后复测用户级 JSONB 行锁、完整文档读写和大工作区响应。

无数据库的健康检查在 20 并发时约 4,928–5,756 请求/秒，说明驱动器可以产生高于当前业务吞吐的负载；但临时池20高吞吐阶段驱动器已接近占用一个 CPU 核心，后续容量测试应拆分驱动器与服务机器。

首轮采集了约 79 秒的进程资源样本，未覆盖最初所有阶段：Go 工作集峰值约 63.8 MiB、私有内存 67.9 MiB；Next.js 工作集约 182.4 MiB；驱动器工作集约 240.6 MiB。样本不能证明不存在长期内存泄漏，PostgreSQL 各进程工作集也不能简单相加作为独占内存。

## 复现

先按第 06 章启动现有 PostgreSQL。账号需具备创建测试数据库的权限；脚本拒绝连接非本机或非本项目的原始数据库，且要求 18080/18081 空闲。不要同时运行常规后端进程。

```powershell
pnpm exec next build services/control
Push-Location services/cloud
go build -o ../../output/load-test/cloud.exe .
Pop-Location
node --test scripts/load-test.test.mjs
node scripts/load-test.mjs               # 完整短时基线
node scripts/load-test.mjs --diagnose    # 连接数与等待采样
```

脚本沿用 `.env.local` 的本机数据库连接与服务端密钥，但使用自己创建的临时库和测试身份；原管理员不参与压测。每次输出位置为 `output/load-test/<runID>/results.json`，不包含密码、Session 凭据或 JWT。新库在运行增量迁移前出现 SDK 缺表提示属于预期准备过程。

当前默认构建已包含正式连接池配置，无需临时副本。复现优化前基线或历史临时实验需从上述优化前提交取源码，并在独立目录构建，避免把优化后代码误当作优化前基线。
