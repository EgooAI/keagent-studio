# 管理员后台单机部署

在 DJK（Ubuntu 22.04、amd64）上沿用现有 Caddy 和 Docker Compose，部署 AI来客管理后台、Next.js 认证、Go 业务和独立的 PostgreSQL 容器。管理员和测试账号使用邮箱与密码登录，测试账号由后台创建。

| 入口                              | 服务                                   |
| --------------------------------- | -------------------------------------- |
| `https://<公网 IPv4 或域名>/`     | Caddy 提供管理后台静态页面             |
| `/api/*`                          | Caddy 转发到 Next.js `127.0.0.1:18180` |
| `/v1/*`、`/health`                | Caddy 转发到 Go `127.0.0.1:18181`      |
| `127.0.0.1:15432/keagent_staging` | PostgreSQL 容器的宿主机回环入口        |

内测可直接使用阿里云控制台显示的公网 IPv4 或绑定的弹性公网 IP。下文的 `203.0.113.10` 是示例地址，请替换成实际公网 IPv4。保留 SSH 管理入口，在安全组开放 TCP 80 和 443。AI来客的三个回环端口与太和使用的 `18080`、`18081` 和 `5432` 错开。

已准备域名时也可直接用域名部署。将域名的 A 记录指向服务器，配置 AAAA 记录时也确认 IPv6 可达，然后将 `admin_host` 设为该域名。

## 1. 准备主机与部署密钥

以下命令由可使用 `sudo` 的非 root 运维账号执行。安装系统范围内可用的 Node.js 24 和 Go 1.25.4 或更高版本，将 Node.js 放入系统服务可用的路径，如 `/usr/bin` 或 `/usr/local/bin`。先核对已有 Caddy、Docker 和 Compose。 [Node.js 安装](https://nodejs.org/en/download) · [Go 安装](https://go.dev/doc/install)

如果目前只有 root 登录入口，可以在现有 SSH 会话创建运维账号后切换。已有运维账号时直接使用该账号。

```sh
adduser keagent-deploy
usermod -aG sudo keagent-deploy
su - keagent-deploy
```

```sh
sudo apt-get update
sudo apt-get install -y ca-certificates git curl openssl openssh-client
sudo npm install --global pnpm@10.33.3
node --version
go version
pnpm --version
systemctl is-active caddy && systemctl is-active docker
sudo docker compose version
sudo ss -H -lnt '( sport = :15432 or sport = :18180 or sport = :18181 )'
```

首次部署时，最后一条检查应无输出。若有监听，先确认归属再决定端口分配。

首次部署时创建系统账号和目录。以下命令把发布目录交给当前运维账号构建，服务以 `keagent` 运行。

```sh
getent passwd keagent >/dev/null || sudo useradd --system --user-group --no-create-home --shell /usr/sbin/nologin keagent
sudo install -d -m 0755 /opt/keagent
sudo install -d -m 0755 -o "$(id -u)" -g "$(id -g)" /opt/keagent/releases
sudo install -d -m 0700 /etc/keagent
sudo -u keagent env PATH=/usr/local/bin:/usr/bin:/bin node --version
```

在运维账号下为 AI来客生成专用密钥，首次生成时确认目标文件名未被使用。通过仓库的 **Settings → Deploy keys → Add deploy key** 粘贴 `keagent_deploy.pub`，保持 **Allow write access** 未勾选。私钥保存在运维账号的主目录，只由该账号用于拉取。 [GitHub Deploy keys](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/managing-deploy-keys#using-multiple-repositories-on-one-server)

```sh
install -d -m 0700 ~/.ssh
ssh-keygen -t ed25519 -C 'keagent-studio@DJK' -f ~/.ssh/keagent_deploy
cat ~/.ssh/keagent_deploy.pub
touch ~/.ssh/config
chmod 0600 ~/.ssh/config
```

编辑运维账号的 `~/.ssh/config`，在通用规则前加入以下独立配置块，保留已有的 `github-deploy` 等条目。

```sshconfig
Host github-keagent
    HostName github.com
    User git
    IdentityFile ~/.ssh/keagent_deploy
    IdentitiesOnly yes
    StrictHostKeyChecking yes
```

首次检查仓库读取权限时，如收到主机信任提示，先将显示的指纹与 GitHub 官方指纹核对，一致后再确认。命令应返回 `refs/heads/main`。 [GitHub 主机指纹](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/githubs-ssh-key-fingerprints)

```sh
git -c core.sshCommand='ssh -o StrictHostKeyChecking=ask' \
  ls-remote --exit-code git@github-keagent:EgooAI/keagent-studio.git refs/heads/main
```

## 2. 构建发布版本

使用配置了部署密钥的运维账号执行。选择包含 `deploy/admin/` 配置的已提交版本，重复部署时以新目录构建，再切换 `current`。后续命令沿用同一终端的 `release` 和 `admin_host`。

```sh
umask 022
admin_host=203.0.113.10
revision=origin/main
release="/opt/keagent/releases/$(date -u +%Y%m%dT%H%M%SZ)"
git clone git@github-keagent:EgooAI/keagent-studio.git "$release"
cd "$release"
git checkout --detach "$revision"
git rev-parse HEAD

ELECTRON_SKIP_BINARY_DOWNLOAD=1 pnpm install --frozen-lockfile
VITE_API_MODE=live VITE_AUTH_API_URL='' VITE_GO_API_URL=/ \
  pnpm --filter @keagent/admin build
pnpm --filter @keagent/control build
mkdir -p output
(cd services/cloud && go build -o ../../output/keagent-cloud .)

test -f apps/admin/dist/index.html && test -f services/control/.next/BUILD_ID && test -x output/keagent-cloud
```

`VITE_AUTH_API_URL=''` 和 `VITE_GO_API_URL=/` 让后台分别请求当前站点的 `/api/*` 和 `/v1/*`，同一套静态文件可用于 IP 和域名。运行时密钥保存在 `/etc/keagent/`，构建使用的是新检出的目录。

## 3. 启动数据库并初始化认证

### 3.1 创建独立测试库

在发布目录执行下列首次安装命令。用 `openssl rand -hex 24` 生成容器内 `postgres` 超级用户的密码，填入 `postgres.env` 的 `POSTGRES_PASSWORD`。Compose 使用项目名 `keagent-postgres` 和独立的持久化数据卷，宿主机只在 `127.0.0.1:15432` 发布数据库端口。

```sh
sudo install -m 0644 deploy/admin/compose.postgres.yaml /etc/keagent/compose.postgres.yaml
sudo install -m 0600 deploy/admin/postgres.env.example /etc/keagent/postgres.env
sudoedit /etc/keagent/postgres.env
sudo install -m 0644 deploy/admin/keagent-db.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl start keagent-db
sudo docker compose -f /etc/keagent/compose.postgres.yaml ps postgres
```

确认容器为 `healthy`。再单独生成一个应用密码，进入容器内的 `psql` 创建应用角色和数据库。执行 `\password` 时输入应用密码。

```sh
sudo docker compose -f /etc/keagent/compose.postgres.yaml exec --user postgres postgres \
  psql -X --set=ON_ERROR_STOP=on --dbname=postgres
```

```sql
CREATE ROLE keagent LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE;
\password keagent
CREATE DATABASE keagent_staging OWNER keagent;
\q
```

### 3.2 运行认证迁移和首个管理员初始化

在发布目录执行以下首次安装命令。后续保留已有的运行环境文件和密钥。

```sh
sudo install -m 0600 deploy/admin/keagent.env.example /etc/keagent/keagent.env
sudo install -m 0600 deploy/admin/bootstrap.env.example /etc/keagent/bootstrap.env
sudoedit /etc/keagent/keagent.env
sudoedit /etc/keagent/bootstrap.env
```

| 文件及变量                                                             | 填写值                                                                                        |
| ---------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `keagent.env` 的 `DATABASE_URL`                                        | `postgresql://keagent:应用密码@127.0.0.1:15432/keagent_staging`，使用上一步的十六进制应用密码 |
| `BETTER_AUTH_SECRET`                                                   | `openssl rand -hex 32` 生成一次，升级时继续使用                                               |
| `BETTER_AUTH_URL`、`JWT_ISSUER`、`TRUSTED_ORIGINS`                     | 同一个对外 HTTPS 源（`https://$admin_host` 对应的实际值），末尾无 `/`                         |
| `JWT_AUDIENCE`                                                         | `keagent-api`                                                                                 |
| `JWKS_URL`                                                             | `http://127.0.0.1:18180/api/auth/jwks`，Go 从同机认证服务取公钥                               |
| `ALLOW_LEGACY_GATEWAY`                                                 | `false`                                                                                       |
| `AI_CONFIG_ENCRYPTION_KEY`                                             | `openssl rand -base64 32` 生成一次，用于后台保存供应商配置，升级时继续使用                    |
| `bootstrap.env` 的 `BOOTSTRAP_ADMIN_EMAIL`、`BOOTSTRAP_ADMIN_PASSWORD` | 首位管理员的邮箱和唯一强密码，密码至少 8 字符，可用 `openssl rand -hex 24` 生成               |

激活发布目录并安装应用服务。应用服务依赖 `keagent-db`，由 systemd 等待数据库健康后再启动。先运行认证迁移和管理员初始化，再启动两个常驻服务。

```sh
sudo ln -sfn "$release" /opt/keagent/current.next
sudo mv -Tf /opt/keagent/current.next /opt/keagent/current
sudo install -m 0644 deploy/admin/keagent-auth-setup.service \
  deploy/admin/keagent-control.service deploy/admin/keagent-cloud.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl start keagent-auth-setup && sudo systemctl enable --now keagent-control keagent-cloud
sudo systemctl is-active keagent-control && sudo systemctl is-active keagent-cloud
```

初始化服务是一次性任务。认证迁移和创建管理员完成后，任务会退出。常驻服务读取 `keagent.env`，Go 启动时创建或更新业务表。`bootstrap.env` 在浏览器验证初始管理员可登录后删除。再次初始化时，同邮箱的管理员账号可继续使用原密码。若邮箱已属于普通账号，初始化会报错，需要换一个邮箱。

空库首次初始化时，认证 SDK 可能在迁移前记录 `Database schema mismatch`。以 `systemctl start keagent-auth-setup` 的退出状态和日志中的 `认证迁移完成。` 为准。

## 4. 配置 Caddy 并验证 HTTPS

在同一发布目录复制站点模板。若现有 Caddy 已为该 IP 或域名定义站点，合并该站点的路由。

```sh
sudo install -d -m 0755 /etc/caddy/sites-enabled
sudo install -m 0644 deploy/admin/Caddyfile /etc/caddy/sites-enabled/keagent-admin.caddy
sudoedit /etc/caddy/sites-enabled/keagent-admin.caddy
sudoedit /etc/caddy/Caddyfile
```

把站点文件首行的 `admin.example.com` 改成实际的 `admin_host`。在主 `/etc/caddy/Caddyfile` 文件的顶层加入一次 `import /etc/caddy/sites-enabled/*.caddy`，保留已有站点。使用域名时，Caddy 按默认方式申请 HTTPS 证书。使用公网 IPv4 时，在 AI来客站点块内部加入以下配置，让 Caddy 使用 Let's Encrypt 的短期 IP 证书。HTTP 验证需要公网能访问 TCP 80，测试客户端通过 443 访问。 [Let's Encrypt IP 证书](https://letsencrypt.org/2026/01/15/6day-and-ip-general-availability/) · [Caddy TLS 配置](https://caddyserver.com/docs/caddyfile/directives/tls#issuers)

```caddyfile
tls {
	issuer acme https://acme-v02.api.letsencrypt.org/directory {
		profile shortlived
		disable_tlsalpn_challenge
	}
}
```

DJK 的公网地址和网卡内网地址不同。IP 客户端一般不会在 TLS 握手里发送 SNI，需要在主 Caddyfile 开头的全局块设置 `default_sni`，值与 AI来客站点使用的公网 IPv4 一致。已有全局块时把该行合并进去。 [Caddy `default_sni`](https://caddyserver.com/docs/caddyfile/options#default-sni)

```caddyfile
{
	default_sni 203.0.113.10
}
```

```sh
sudo -u caddy test -r /opt/keagent/current/apps/admin/dist/index.html
sudo caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile &&
  sudo systemctl reload caddy
```

从外网终端验收，先设定实际公网 IPv4 或域名。服务器回连自己的公网 IP 可能受云网络限制。

```sh
admin_host=203.0.113.10
curl -sS -o /dev/null -w '%{http_code} %{redirect_url}\n' "http://$admin_host/"
curl -fsS "https://$admin_host/" -o /dev/null
curl -fsS "https://$admin_host/health"
curl -fsS "https://$admin_host/api/auth/jwks"
curl -sS -o /dev/null -w '%{http_code}\n' "https://$admin_host/v1/admin/users/list"
```

预期 HTTP 跳转到 HTTPS，HTTPS 首页响应成功，`/health` 返回 `{"status":"ok"}`，JWKS 返回含 `keys` 的 JSON，无会话访问用户列表返回 `401`。Caddy 会在后台申请并续期证书。首次申请若尚未完成，可查看 `sudo journalctl -u caddy -n 80 --no-pager`。证书通过校验后再登录。

## 5. 浏览器验收

1. 打开当前 HTTPS 入口的 `/#/admin/dashboard`，用初始管理员邮箱和密码登录。确认「管理工作台」和「用户与设备」能加载，覆盖从认证换取令牌到业务 API 查询。验证完成后运行 `sudo rm -- /etc/keagent/bootstrap.env`，把管理员密码留在密码管理器。
2. 进入「用户与设备 → 创建用户」，填写姓名、测试邮箱和至少 8 个字符的初始密码。列表应显示该账号为普通用户。
3. 在另一个浏览器配置文件中用新账号登录管理后台，确认页面显示「当前账号没有管理权限」。保持该会话在线。
4. 在管理员会话对该账号点「强制退出」。刷新普通用户会话，应回到登录页。在「操作记录 → 账号操作」确认操作记录。测试客户端时，也用新账号连接同一 HTTPS 源，确认强制退出后的下一次云端访问要求重新登录。
5. 如需测真实业务，先配置测试供应商凭证和少量赠送积分，再跑一条短任务，核对任务账单和流水。仅验收管理员功能时可用账号和审计流程完成验证。

故障排查先检查本机 Go、认证公钥和服务日志。

```sh
curl -fsS http://127.0.0.1:18181/health
curl -fsS http://127.0.0.1:18180/api/auth/jwks
sudo docker compose -f /etc/keagent/compose.postgres.yaml ps postgres
sudo journalctl -u keagent-db -u keagent-auth-setup -u keagent-control -u keagent-cloud -u caddy -n 120 --no-pager
sudo ss -ltn
```

## 6. 升级、备份与回退

先按第 2 节构建新目录。安排测试停机窗口，记录当前版本并停止两个应用服务，再快照数据库与运行环境文件。使用具备主机权限的运维账号执行。

```sh
previous=$(readlink -f /opt/keagent/current)
backup="/var/backups/keagent/$(date -u +%Y%m%dT%H%M%SZ)"
sudo install -d -m 0700 "$backup"
sudo systemctl stop keagent-cloud keagent-control
printf '%s\n' "$previous" | sudo tee "$backup/previous-release" >/dev/null
sudo sh -c 'umask 077
  docker compose -f /etc/keagent/compose.postgres.yaml exec -T --user postgres postgres \
    pg_dump -Fc keagent_staging > "$1/keagent_staging.dump"' sh "$backup"
sudo install -m 0600 /etc/keagent/keagent.env "$backup/keagent.env"
sudo install -m 0600 /etc/keagent/postgres.env "$backup/postgres.env"
sudo sh -c 'docker compose -f /etc/keagent/compose.postgres.yaml exec -T --user postgres postgres \
  pg_restore --list < "$1/keagent_staging.dump"' sh "$backup" >/dev/null
```

备份成功后再发布。备份中的 `keagent.env` 含 `BETTER_AUTH_SECRET` 和 `AI_CONFIG_ENCRYPTION_KEY`，与数据库快照一并存放在受限备份位置。跨主机恢复需要先建立 `keagent` 角色及对应的应用连接凭据。若备份步骤失败，保留旧 `current` 并启动旧服务。

进入新发布目录，按第 3.2 节的激活命令切换 `current` 和安装应用 unit。应用升级沿用 `/etc/keagent/` 的运行配置和数据库数据卷。重新执行 `keagent-auth-setup` 后启动两个常驻服务，再复查 HTTPS 和浏览器。Caddy 站点配置有变更时按第 4 节验证并重载。

回退前确认旧版本使用本手册的 DJK 端口和容器数据库，并且兼容新版本写入的数据库结构。满足这些条件时，在仍设有本次 `$backup` 路径的终端执行以下命令，再复查 HTTPS 和浏览器。

```sh
previous=$(sudo cat "$backup/previous-release")
test -x "$previous/output/keagent-cloud"
sudo systemctl stop keagent-cloud keagent-control
sudo ln -sfn "$previous" /opt/keagent/current.next
sudo mv -Tf /opt/keagent/current.next /opt/keagent/current
sudo install -m 0644 "$previous/deploy/admin/keagent-auth-setup.service" \
  "$previous/deploy/admin/keagent-control.service" "$previous/deploy/admin/keagent-cloud.service" /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl start keagent-control keagent-cloud
```

结构不兼容时，先保留当前数据库副本，用升级前的备份在新建的隔离数据库上演练恢复，验证登录和业务数据后再决定切换，恢复点之后的写入需另行核对。

## 7. 从公网 IP 切换到域名

1. 设置域名的 A 记录指向原公网 IPv4。按第 6 节备份测试数据库和运行配置，并另外保留本次改动前的 Caddy 配置副本。
2. 把 AI来客站点首行改为新域名，移除该站点的短期 IP `tls` 配置和专为内测添加的全局 `default_sni`。验证并重载 Caddy，确认新域名证书通过校验。
3. 把 `/etc/keagent/keagent.env` 里的 `BETTER_AUTH_URL`、`JWT_ISSUER`、`TRUSTED_ORIGINS` 一起改为 `https://新域名`。继续使用原数据库和密钥。执行 `sudo systemctl restart keagent-control keagent-cloud`，再按第 4、5 节验收。按本手册构建的后台静态文件可以直接使用。旧版如果在 `VITE_GO_API_URL` 中写死了地址，先按第 2 节用同源配置重建。
4. 如果已发出桌面测试包，将其认证和业务地址一起改为新域名。网页和桌面端都用原账号在新地址重新登录。
